Preface

Within the narrative and theoretical scope of the book, this appendix serves primarily to demonstrate how a memory-safe, C-successor language ought to define its semantic boundaries, rather than to provide a drop-in replacement for a rigorous ISO-level standard.

In this context, CobaltC can best be described as a systems language designed to address the safety problems of C while adopting a more robust structural model.

If nothing else, it illustrates the exact pain points and formal guarantees required to make a safe systems programming language actually function.

As argued throughout The Wrong Memory essays, attempting to tack a "safe subset" onto an inherently unsafe language usually fails because the core language semantics still allow invariant violations. By embedding ownership and borrowing into the core type system, CobaltC makes safety an intrinsic property of the language rather than an optional discipline imposed upon it.

CobaltC unashamedly draws on the ownership and memory-safety techniques demonstrated by Rust. Although Rust isn't the origin of most of these ideas, its significant contribution was demonstrating how they could be combined into a practical, high-performance systems language. CobaltC adopts that safety architecture without attempting to reproduce Rust's syntax or overall language philosophy. Instead, it applies the broader body of ideas to the problem identified in Appendix II: making semantic invariants such as ownership, lifetime, aliasing, mutability, and bounds properties that the compiler can represent and enforce, rather than obligations the programmer must maintain by convention.

The CobaltC Proposition

The distinction is perhaps easiest to see in a deliberately small example. Allocate some storage, keep a second name for it, destroy the storage, and use the second name.

C accepts this program without complaint — GCC and Clang compile it silently even with every common warning enabled. At best, a modern compiler may warn about a case this obvious; move the free behind one function call and the warning disappears, while the bug does not. The program compiles, runs, and reads the wrong memory. The fact that alias still refers to freed storage exists only in the programmer's head.

The same program, the same shape — allocate, alias, destroy, use — and it does not run. The fact that alias still points into data lives in the language, so destroying data underneath it is refused before the program starts, with a named diagnostic: heuristic warnings on one side, a semantic guarantee on the other.

"You have the power. Let’s prove you’re exercising it correctly."

The guarantee is not bought by removing capability. Below, two exclusive (mutable) references into the same array are held at once — something safety-minded languages commonly refuse — legal here because the compiler has proven they touch disjoint elements. CobaltC forbids the crime, not the capability.

CobaltC retains the same fine-grained control, while allowing the compiler to establish the relevant safety properties: a and b refer to distinct elements of values, their mutable accesses are disjoint, and the underlying storage remains owned by values.
