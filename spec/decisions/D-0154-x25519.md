# D-0154 — X25519 key agreement in `std::crypto`

Status: ACCEPTED (2026-10-04, the owner: "then D-0154 X25519 once that passes", the third step of the agreed crypto roadmap toward a DNS-over-TLS client)
Kind: Decision (`spec/02-schema.md`)
Governed by: `CobaltC_Master_Instructions.md` §1, §9 (the std helper admission test)
Depends on: D-0151 (`std::crypto`), D-0153 (`diag.crypto-length`, `[Constant-Time]`), D-0142 (`os_random_bytes`)
Affects: `spec/21` §0, §2m (4.19.0), `spec/conformance.md` (3.144.0), the guide §21, `impl/std/crypto.cb`; `CHG-0182`

## Problem

Two programs that have never met must agree on a secret over a network
anyone can read. Each makes a private key, sends the matching public
key, and computes the same shared secret from its own private key and
the other's public key; an eavesdropper who sees both public keys cannot.
TLS 1.3's handshake does exactly this, and X25519 (RFC 7748) is the
group every TLS 1.3 implementation offers first.

## Candidate mechanisms

1. **X25519** (RFC 7748): Curve25519's Montgomery ladder, 255 identical
   steps with a swap by mask; field arithmetic modulo 2^255 − 19 in five
   51-bit limbs through `u128`, which the language has. No point
   validation needed beyond refusing an all-zero result. Selected.
2. **ECDH over P-256** (NIST). Needed for some peers, harder to make
   constant-time (incomplete addition formulas, point validation). A
   later record, with ECDSA P-256.
3. **A key-pair type** (Go's `ecdh.PrivateKey`). Three functions on
   32-byte values say the same with no new type. Rejected.

## Selected design

`spec/21` §2m `[X25519]`, in `std::crypto`, written in CobaltC:

- `x25519_private_key() : array<u8, 32>`: 32 bytes from
  `os_random_bytes`, so a key is never drawn from `Rng`.
- `x25519_public_key(private_key) : array<u8, 32>`: the private key
  times the base point (u = 9).
- `x25519(private_key, public_key) : Option<array<u8, 32>>`: the shared
  secret, or `None` when it is all zeros, which a public key of small
  order produces and which RFC 7748 §6.1 and TLS 1.3 forbid using. An
  `Option`, as `chacha20_poly1305_open` gives one: one way to fail.
- Keys are slices; a length other than 32 is `diag.crypto-length`. The
  scalar is clamped as RFC 7748 says; the top bit of a public key is
  ignored.
- **Constant time** (`[Constant-Time]`): the ladder's 255 steps and the
  inversion's fixed exponent run the same way for every key; swaps are
  by mask.
- **Verification:** RFC 7748 §5.2's two vectors and the iterated vector
  after 1 and 1000 rounds, §6.1's Alice-and-Bob exchange (both public
  keys and the shared secret), the all-zero point refused, and a sweep
  of random keys against Python's `cryptography` package under all three
  tools.

Not adopted: X448 (not needed by the client); P-256 ECDH (above);
Ed25519 signatures, a later record.

## Compatibility impact

Additive: three exported functions in `std::crypto`.

## Revisit conditions

- ECDH over P-256 and P-384, with ECDSA, when a peer requires them.
- X448, if a protocol a program speaks requires it.
