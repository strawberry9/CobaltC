## Problem

Since D-0276 the toolchain exists twice:

| Part | Rust | CobaltC |
|---|---|---|
| Front end (lexer, parser, resolution, folding, type check) | `impl/src/`, about 17,200 lines, shared by `coby` and `cobc` | `impl/selfhost/front/`, about 33,300 lines (plus the generated `prelude.cb`), shared by `cbc` and `cbparse` |
| Code generator and driver | `impl/cobc/src/`, about 24,500 lines | `impl/selfhost/back/` and `cbc/`, about 54,200 lines |
| Evaluator | `impl/src/interp*`, about 11,300 lines (`coby`) | none |
| Runtime | `impl/cbrt/` (`libcbrt.a`) | none |

A change to the front end is made in `impl/src/` and in `selfhost/front/`; a change to the lowering in
`impl/cobc/` and in `selfhost/back/`. `std`, the diagnostics registry and the runtime are single copies
(`front/prelude.cb` is generated by `coby --prelude-summary`). The two copies are held together by
`compare_parser.sh` (the front end's dumps against `coby`'s, byte for byte, on every tracked file and seven
mutants of each), `compare_c.sh` (the C against `cobc`'s) and `fixpoint.sh`.

The question is whether to keep paying for every language change twice, and if not, which copy goes.
Two facts shape every answer:

- **The Rust tools are the fast ones.** `cbc` compiles 15 to 45 times more slowly than `cobc` (its own
  C: about 18 minutes against 26 seconds, after Update 134), and the compiled front end runs 18 to 45 times
  `coby`'s instructions (tinyos, dns_over_http); the cause is the runtime's object tracking (P4, the next phase). The suites, the battery and
  day-to-day work all run on the Rust tools' speed.
- **The two copies are the strongest evidence the project has.** Two implementations written separately
  and required to agree byte for byte have found real bugs in both (`CHG-0345`, `CHG-0347`, `CHG-0349`,
  `CHG-0351`, `CHG-0369` among them). The executable model (`cobmodel`, D-0219) and the conformance suite
  are independent of both and stay whatever is decided.

## Options

1. **Keep both (today).** Every front-end and lowering change is written twice; the compare scripts and the
   fixed point say when the copies agree.
   - For: the strongest cross-check stays; nothing to build or migrate; the fast tools stay the working
     tools.
   - Against: every language change costs roughly twice the implementation work, and the CobaltC copy is
     the larger and the slower to test; the cost grows with the language.

2. **Retire `cobc` only.** `cbc` becomes the only compiler; `coby` and its Rust front end stay. The
   lowering exists once (in CobaltC); the front end still exists twice (`coby`'s and `cbc`'s).
   - For: removes the larger duplicated part (the lowering and driver), the one D-0276 already names as
     made "in two places until `cobc` is retired"; `compare_parser.sh` against `coby` still checks the
     front end.
   - Against: the C loses its byte-for-byte oracle; a lowering bug is then caught only by behaviour
     (the compiled conformance suite, the differential tests against `coby`, the fixed point). Needs, first:
     (a) P4, so that the compiled suites and the battery run at a bearable speed with `cbc`; (b) `cobc`'s
     tests (`impl/cobc/tests/`, already `COBC=`-driven) moved to drive `cbc` by default; (c) a **bootstrap
     seed** — with no `cobc`, building `cbc` from a clean checkout needs a `cbc` from somewhere. Choices:
     (i) keep `cobc` frozen at the retirement commit, used only to build the first `cbc` (it then lags the
     language, so the seed must be a `cbc` source old enough for it to compile, chained forward);
     (ii) publish prebuilt `cbc` executables per target with each Update, outside git;
     (iii) publish `cbc`'s own C (about 110 MB in the default form) as a release file, outside git, built
     with the C compiler alone.

3. **One toolchain in CobaltC.** As 2, and port `coby`'s evaluator to CobaltC over `selfhost/front/`; the
   Rust front end goes. Rust remains only in `cbrt` (and `cobmodel`).
   - For: every language change is made once; the project is written in its own language end to end.
   - Against: a port of about 11,300 lines of evaluator plus `coby`'s I/O, thread scheduling and
     `--explore`; the independent second front end is gone, so the evidence for the front end is the
     model, the conformance suite and review alone; the interpreter would run at compiled-CobaltC speed
     until P4 pays off. The bootstrap seed of option 2 is needed as well.

4. **Freeze the Rust tools at an edition.** New language features go into the CobaltC tools only; `coby`
   and `cobc` stay as the oracle for the language as it was at the freeze, and the compare scripts skip
   the programs that use anything newer.
   - For: no work is written twice from the freeze on, without a port.
   - Against: two dialects in the tree; the cross-check shrinks with every feature; the fast tools no
     longer accept the current language, so day-to-day work moves to the slow ones anyway. Of the four,
     the one that drifts worst.

5. **The Rust toolchain leads, the CobaltC toolchain follows at milestones** (added 2026-10-25, when D-0281
   opened a period of heavy change to the front end, the lowering and the runtime). Every language and
   runtime change lands in `coby`, `cobc` and `cbrt` only. `impl/selfhost/` stays at the edition of
   Update 135: it builds, its fixed point is recorded at that edition, and its checks (`compare_parser.sh`,
   `compare_c.sh`, `fixpoint.sh`) run against the Rust tools of that edition, not against each change. At each
   of D-0281's phase boundaries the settled changes are ported forward and the fixed point is re-established.
   - For: D-0281 is prototyped and revised in quick measure-and-revise loops at the Rust tools' speed, each
     written once; `cbc` holds the most stored views in the corpus, so it is a subject of D-0281 and is
     reshaped once against settled rules instead of with every revision; `cbc`'s cost is the runtime model
     D-0281 replaces, so the `cbc` ported after phase 3 is the first fast one, which is when retiring `cobc`
     (D-0276) becomes practical.
   - Against: the two-copy cross-check pauses between milestones (`coby` against `cobc`, the model sample
     and the conformance suite stay); the port grows with the lag, hence a port at every phase boundary,
     not once at the end; for a while the self-hosted compiler accepts an older edition, which the README
     and `impl/STATUS.md` must say.

## Decision

Option 5. The Rust toolchain is the reference during D-0281; the CobaltC toolchain is ported forward at each
D-0281 phase boundary, and is never left more than one phase behind. Retiring `cobc` (option 2), the bootstrap
seed and the place of `cbparse` are decided again after D-0281's phase 3, with a fast `cbc` in hand. The
earlier recommendation (option 1 now) assumed the language was not entering a period of many front-end changes;
the draft named that as what would change it, and D-0281 is that period.

**Amendment (2026-10-28, under D-0281's delegation).** The CobaltC toolchain is ported forward once, after D-0281's
phase 3, not at each phase boundary. Phases 1 to 3 are now grouped into three Updates whose changes overlap (the
static pass's frame rules, the decided lowering, then a new tier-D runtime): a port at each boundary would port
code the next phase rewrites. The single port includes `cbc --emit-c -o` (as `cobc` has it) and the closure and
spawn rules; until then `cbc` keeps paths for every closure and spawn (D-0288, D-0289). D-0281 §23.

## Recommendation (as drafted, 2026-10-24, superseded by the decision)

Option 1 now, and option 2 as a later decision once its preconditions hold: P4 has brought `cbc` within
the plan's working bound (ten times `cobc`, D-0276) or better, `cobc`'s tests drive `cbc`, and a bootstrap
seed is chosen (of (i)–(iii), (iii) keeps the build to a C compiler alone and needs no frozen Rust, so it
is the recommendation when that day comes). Option 3 is not recommended for now: it trades away the
independent front end, which has been the main source of findings, for a saving that matters only once the
language stops changing quickly. Option 4 is not recommended.

What would change the recommendation: if the language is entering a period of many front-end changes,
the cost of option 1 rises and option 2's preconditions (P4 above all) become the work to do first.
