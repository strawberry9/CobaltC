# D-0160 — `std::x509`: DER, certificates, and chain verification

Status: ACCEPTED (2026-10-04, the owner: "proceed with the entire roadmap using your discretion", on the crypto roadmap agreed toward a DNS-over-TLS client)
Kind: Decision (`spec/02-schema.md`)
Governed by: `CobaltC_Master_Instructions.md` §1, §9 (the std helper admission test)
Depends on: D-0140 (`DateTime`), D-0144 (`IpAddr`), D-0151, D-0158, D-0159
Affects: `spec/21` §0, §2n (new) (4.25.0), `spec/conformance.md` (3.150.0), the guide §21, `impl/std/x509.cb` (new), `impl/std/std.cb`, `impl/src/prelude.rs`; `CHG-0188`

## Problem

A TLS client must decide whether the certificates a server sends prove
that it is the server it claims to be: each signed by the next up to a
root the client trusts, each in date, each issuer a certificate
authority, and the leaf naming the host.

## Candidate mechanisms

1. **A general ASN.1 library** (Go's `encoding/asn1` with reflection).
   CobaltC has no reflection; a decoder per structure is what remains.
2. **A DER element reader and a certificate parser for what
   verification needs**, plus RFC 5280 path validation as a client
   performs it. Selected.

## Selected design

`spec/21` §2n, `rule.stdlib.x509`, a new submodule `std::x509`:

- `Der` and `der_read(buf, at)`: one DER element, strict (minimal
  lengths, no indefinite form, at most four length bytes).
- `Certificate::parse(der)`: the signed part, issuer and subject (their
  DER, compared whole), the common name, validity (UTCTime and
  GeneralizedTime as RFC 5280 restricts them), subject alternative names
  (DNS names and IP addresses), basic constraints, key usage, extended
  key usage (server authentication), the key (`CertKey`: RSA, EC P-256
  or P-384, or unsupported), the signature scheme (`SignatureScheme`:
  RSA PKCS #1 v1.5, RSA-PSS with SHA-2 and MGF1, ECDSA; SHA-1 and MD5
  are unsupported) and the signature. An unknown critical extension
  marks the certificate unusable (policies and name constraints are
  tolerated unread).
- `certificates_from_pem(text)`, `TrustStore` (`new`, `add`,
  `from_pem_file`, `system`: the usual bundle files on Unix; on Windows
  a program passes a bundle), `verify_signature`.
- `Certificate::matches_host`: DNS names case-insensitively with a
  wildcard for one whole leftmost label (RFC 6125), IP addresses for an
  address literal; the common name is never consulted.
- `verify_chain(leaf, intermediates, roots, host, now)`: host, server
  usage, dates, then upward by issuer name and signature through the
  intermediates (any order) to a root, each issuer a CA allowed to sign
  certificates and within its path length; at most ten certificates.
  `CertError` names the reason (`HostMismatch`, `Expired`,
  `UnknownAuthority`, …; variant names unique in `std`).

Verified with an openssl-made PKI (EC P-384 root, RSA-PSS-signing
intermediate, EC and RSA leaves) as a case, every refusal reason, the
system's 121 roots parsed (115 self-signatures verified; the rest SHA-1
or P-521), and real resolvers' chains during the TLS tests.

Not adopted: revocation (CRL, OCSP), name constraints enforcement,
policy checking, certificate creation.

## Compatibility impact

Additive: a new submodule.

## Revisit conditions

- Windows' system store, read natively, if programs there need it.
- Name constraints and OCSP stapling, if a deployment requires them.
