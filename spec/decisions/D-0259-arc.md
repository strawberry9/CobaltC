# D-0259 — `Arc<T>`: shared ownership across threads

## Problem

A spawned thread shares state only by reference, and a reference does not outlive its frame: a function
that spawns a worker over a local atomic, counter or mutex and returns the handle faults at its frame end
(`diag.destroy-while-aliased`), so a long-lived worker pool, a server that hands back its handle, or any
thread that must outlive the frame that made what it shares has no way to share it. The only way out is to
move everything into one thread. `Rc` is explicitly not thread-safe (its counts are plain integers). With
atomics (D-0249) a reference-counted handle whose counts are atomic is writable in `std`.

## Options

- **A. Leave it.** Share by reference; a thread that must outlive a frame takes everything by move. Simple,
  but the gap above stays, and the pattern it blocks (a pool of workers owning their share of a
  configuration or a result sink) is the common one in servers.
- **B. `Arc<T>` and `ArcWeak<T>` in `std::memory`, beside `Rc`.** `Rc` with `Atomic<usize>` counts: handles
  cloned, moved into threads and dropped there; the value ends once, on whichever thread drops the last
  strong handle. Read-only access (`Arc::get`), so mutation is a `mutex` or an `Atomic` inside, as for `Rc`.
- **C. Make `Rc` itself atomic.** One type; every clone and drop pays an atomic read-modify-write, cheap on
  x86-64 but not free, and `Rc`'s documented single-thread meaning changes.
- **D. `Arc` without a weak handle.** Smaller; a cycle of `Arc`s then has no remedy, and a parent pointer or a
  cache across threads needs the weak form as much as it does for `Rc`.

## Decision

**B.** `Arc<T>` and `ArcWeak<T>`, named by analogy with `Rc` and `Weak`. The box holds two atomic counts:
`count`, the strong handles, and `weak`, the `ArcWeak` handles plus one for the strong handles together, so
the box lives while `weak` is not 0 and the thread whose decrement brings it to 0 frees it, whichever thread
that is; this is what makes the last `Arc::drop` and a concurrent `ArcWeak::drop` or `upgrade` safe without
a lock (`spec/21` §3′). No bound on `T`: what crosses threads inside an `Arc` is subject to the same dynamic
checks as anything reached through a shared reference, so an `Rc` inside an `Arc` cloned from two threads at
once is `diag.aliasing-conflict` at `Rc::clone`'s exclusive borrow, as it is today through `&rc`. `Arc::clone`
is what `clone(&a)` calls (D-0116). No count accessor (Master Instructions §9: a weak handle's `upgrade`
observes liveness).

## Results

Written in CobaltC in `impl/std/memory.cb`, every `unsafe` block covered by a trusted claim (§0's table).
The prototype that preceded it (`stress/atomics_std/arc_proto.cb`) and the conformance cases
(`conf.arc-shared-by-threads`, `conf.arc-last-drop-frees`, `conf.arc-weak`, `conf.arc-thread-outlives-frame`)
run identically under `coby`, `cobc` with GCC and Clang, and both tools' `--explore`; both runtimes let two
threads reclaim the same raw box at once with an atomic inside it, and the value's destructor runs on the
worker that drops last. Two unit tests in `std`, which the guide runs.

## Revisit conditions

A `get_mut` when the count is 1 (Rust's `Arc::get_mut`), if programs ask for it; a `Send`-like bound, if the
dynamic checks ever prove insufficient for a type crossing inside an `Arc`.
