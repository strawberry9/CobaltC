# D-0172 — TLS_AES_256_GCM_SHA384, P-384 and Ed25519 in `std::tls`

Status: ACCEPTED (2026-10-05, the owner: "Yes: AES-256-GCM-SHA384 + P-384")
Kind: Decision (`spec/02-schema.md`)
Governed by: `CobaltC_Master_Instructions.md` §1
Depends on: D-0161 (the TLS 1.3 client), D-0165 (AES-GCM, HelloRetryRequest), D-0166 (HKDF over SHA-384), D-0168 (P-384 key agreement), D-0171 (Ed25519 in certificates)
Affects: `spec/21` §0, §2o (4.37.0), the guide §21, `impl/std/tls.cb`; `CHG-0200`

## Problem

D-0165 deferred TLS_AES_256_GCM_SHA384 and P-384 because no surveyed
server required them; both are in every server's default set, some
deployments allow only AES-256, and some private PKIs are P-384 or
Ed25519 throughout. With the pieces now in `std::crypto`, the client can
offer the full common set.

## Candidate mechanisms

1. **Offer the third suite, the third group (by HelloRetryRequest, as
   P-256) and the Ed25519 signature scheme; the key schedule and
   transcript under the suite's hash.** Selected.
2. **A P-384 (or P-256) share in every ClientHello.** A P-384
   multiplication in every handshake for the few servers that want it.
   Rejected, as in D-0165.

## Selected design

**`spec/21` §2o `[Tls-Client]`:**

- Suites offered: TLS_CHACHA20_POLY1305_SHA256, TLS_AES_128_GCM_SHA256,
  TLS_AES_256_GCM_SHA384; the key schedule, transcript hash, Finished and
  key updates run over the suite's hash (SHA-384 for the last).
- Groups offered: X25519 (with a share), P-256 and P-384 (by
  HelloRetryRequest, a share of the group asked for).
- Signature schemes offered: ECDSA P-256/SHA-256, P-384/SHA-384, RSA-PSS
  with SHA-256/384/512, Ed25519, and the PKCS #1 schemes for
  certificates.
- Alert 40's text names the three suites and three groups.

## Compatibility impact

Additive: every server that completed before still does.

## Revisit conditions

- Client certificates, now that `sign` and `PrivateKey` exist.
- Session resumption and 0-RTT, if latency matters.
