# CobaltC Specification — Reading Guide

This directory is the normative definition of CobaltC (Master
Instructions §13). Every artifact is at version 1.0.0 or later (each
carries its own Version and Change Log; `changes/` records every
normative change since 1.0.0); every entity `ACCEPTED`. This file is a
map, not a normative artifact.

## Edition

**CobaltC specification edition 2026.111401.**

The specification as a whole is identified by its edition,
`YYYY.MMDDnn`: the date it was published (UTC) and a two-digit counter
for that day, starting at 01. Editions before 2026-09-30 were numbered
`YYYY.nnn`, a counter within the year; both forms sort in publication
order, as text and as numbers. A new edition is published whenever an update of the
repository changes anything in this directory; an update that changes
only the implementations, the guide or the examples keeps the edition,
and so does one that changes only `MANIFEST.md` (a battery's or a suite
run's record added after the edition was published, CHG-0256).
Each artifact still carries its own `Version` and Change Log, and each
normative change its `CHG` record; the edition names the set of them
published together. A conformance claim names an edition
(`NAMING-POLICY.md`: "conforms to CobaltC 2026.100306").

**The manifest.** `MANIFEST.md`, generated by `impl/tools/manifest.py`
(D-0212), lists what an edition consists of: the SHA-256 of every file
in this directory, each artifact's Version, the highest decision and
change-record numbers, the conformance cases, the toolchain and result
of the last battery, and the evidence tier. It is regenerated when the
edition is bumped, before the repository is squashed.

**Evidence tiers.** What was done to an edition before it was published,
one word in its row below and in the manifest; a green test run is a
record, not a certificate, and the word says how much of one:
*reviewed* — the text changed and was read; the gate (`impl/gate.sh`,
D-0307) has no green verdict for this tree's inputs (editions before
2026.110204: no test target was run; the rows that say "rapid, no
battery" are this tier);
*tested* — every unit of the gate's *gate* profile has a green verdict
for this tree's inputs: both conformance suites under both
implementations (`cobc` with GCC and Clang), every other test target, the
guide, the book, the showcases, the model sample, the self-hosted
compiler against `cobc`, the lowering's sweep and timings; the manifest
lists each unit's verdict and the run it came from (editions before
2026.110204: the targeted suites as `impl/tools/suites.sh` ran them,
CHG-0256);
*battery* — the *release* profile's units too: the self-hosted fixed
point, the whole-corpus comparisons, `--all-checks`, the debug profile,
the slow cases, the verify modes, the stress programs, sanitizers and
fuzzer (editions before 2026.110204: the staged `impl/battery.sh`, with
the run under `stress/battery_staged/runs` named in the manifest);
*explored to N* — in addition, the thread cases the edition adds were run
under `cobc --explore N` and gave one outcome each;
*modelled* — in addition, the run the tier names compared the model's
sample (`impl/model/sample`, D-0219) with both implementations, and every
outcome they showed was one the model, written from these rules
independently of the implementations, allows. A scoped battery that left
the comparison out (its changes could not alter the outcome) carries the
word from the green run it was scoped against (`CHG-0263`).

**Assurance** (D-0299). `ASSURANCE.md` says what evidence stands behind
the claim that the rules, the compiler and the runtime do what this
specification says: for each obligation a user's trust rests on, what is
proved, checked, tested or trusted, and what a user can check about their
own program (`cobc --certificate`, `cobmodel certify`) without the project's
test suites.

**Stability** (D-0220). `STABILITY.md` says what an edition promises about
the ones after it. The language (*core*: `00`–`20`, `22`, the registries) and
the standard library (*std*: `21`) each carry a mark — *moving*,
*candidate* or *stable* — at the end of each row from D-0220 on, after the
evidence tier; a row without marks is read as both parts moving. Each change
is a *clarification*, a *soundness repair*, *additive* or *breaking (source)*,
and what a part may take depends on its mark.

The register below holds the ten most recent editions; the earlier ones,
unchanged, are in `EDITIONS-HISTORY.md`.

## What is normative

Rules written in CFN (`01-metalanguage.md`) inside `03`–`21`, the
state definition in `04`, the grammar in `22`, the registries, and
the conformance suite. Prose explains; where prose and a rule differ,
the rule wins. Decision records (`decisions/`) are rationale, not
rules.

## Reading order for an implementer

0. `02-schema.md` — how an artifact, a rule and an entity are written;
   then `OVERVIEW.md` (non-normative) — the semantics in prose, section
   by section, each paragraph citing the rules it explains: the state,
   paths, `clash`, the static/dynamic boundary, moves and destruction,
   threads, the trust boundary, `[Standing-Local]`, the safe-program
   theorem and what the executable model covers.
1. `22-surface-syntax.md` — the grammar and the correspondence table
   from each production to its rule.
2. `04-abstract-state.md` — `Σ`, every component, every predicate.
3. `12-type-system.md` — static typing; then `06` §7 for
   representation and the implementation-defined parameters you must
   choose and document.
4. `13` → `05` → `14` → `15` — evaluation: results, `store`, statement
   and block exit, calls and `main`.
5. `08`, `07`, `16`, `09`, `10`, `11` — aliasing, resources and
   destructors, aggregates, references, escape checking, `let`.
6. `14` §6 — `rule.control.flow-analysis`: the exact static/dynamic
   boundary; your implementation must reject exactly the refuted
   instances.
7. `17`, `18`, `19`, `20`, `21` — modules, faults, threads, raw
   pointers and FFI, and the standard library module `std`: its intrinsics and the library
   types written in CobaltC itself (`Vec`, `String`, `HashMap`, `Rc`, `Box` and the rest),
   whose bodies are normative for what they do, not how: `cobc` realizes the most-used
   ones natively (`21` §0). What a claim about `std` rests on — the four assurance
   tiers and the security profile of each security-relevant module — is `21` §0
   "Assurance", non-normative.
8. `conformance.md` — every case with its derivation; `registry/
   diagnostics.md` — every diagnostic you must be able to report.

## What you must decide and document

Listed in `22` §5: `AddrWidth`, byte order, enum discriminant width,
struct padding, `dangling<T>()`, `fn` value encoding, mutex cells,
the reporting form of termination outcomes, calling convention/ABI.
`IMPLEMENTATION-NOTES.md` (non-normative) is the consolidated form of
this list, alongside every point of permitted nondeterminism and every
`unsafe` trust condition, each with its governing rule.

## What the language does not provide

`22` §5's "deliberate absences" and "restrictions". Do not add them
in an implementation; propose them through a `D-XXXX` decision.
